# hermes: подтверждаемое создание и редактирование задач и целей

статус: утверждено пользователем 2026-10-27. реализация, миграции в production, новые credentials и изменения данных этим документом не выполняются.

## 1. зачем и что согласовано

пользователь уже проверил чтение дашборда своим hermes в telegram. следующий этап — управлять задачами и целями в том же чате, не открывая сайт для каждого изменения.

согласованы варианты `1а, 2а, 3а` и первый способ реализации:

- каждое изменение сначала показывается пользователю и сохраняется только после отдельного подтверждения;
- задачи: создание, редактирование названия, описания, даты, плановых минут, сектора, сложности и текста подзадач; без выполнения задач и наград;
- цели: создание, редактирование, приоритеты, переносы между периодами, прогресс, выполнение и возврат; выполненные остаются в своём периоде;
- запись выполняется на сервере и работает при закрытом дашборде; подтверждение — штатными кнопками hermes в telegram;
- удаление задач/целей, изменения трекера, школы, финансов, монет, xp и магазина не добавляются;
- merge, production deployment, включение записи и live mutations — отдельные разрешения, не следствие утверждения дизайна.

это проект с изменениями api, синхронизации, postgres и windows-коннектора, а не добавление флага `write=true` к текущему чтению.

## 2. проверенные исходные условия

на момент подготовки документа:

- рабочая основа — `feature/hermes-dashboard-read`, коммит `cc74d37acfca58c610b257176ec6ffbc8bd82cde`; pr #70 открыт и основан на `main`;
- отдельная ветка документа — `feature/hermes-dashboard-write-design`, поверх указанного коммита; история pr #70 не изменяется;
- `supabase-sync.js` отправляет целые значения через `user_data.upsert`, без compare-and-swap; realtime и polling применяют их по `updated_at`;
- задачи лежат массивами в `goals:yyyy-mm-dd`, цели — в `horizons_goals_v2`; у старых задач нет обязательного постоянного id;
- metadata-only запрос к production подтвердил столбцы `user_data`: `user_id uuid`, `key text`, `value text`, `updated_at timestamptz`; поля версии пока нет;
- локальная миграция `20260728220641_harden_user_data_rls.sql` описывает owner policies и серверный `updated_at`; наличие файла не доказывает её применение. metadata-only проверка production показала rls enabled, legacy policy `Users can manage their own data` с `auth.uid() = user_id` и отсутствие пользовательских triggers у `user_data`. history содержит только `20260727133927_school_mutation_locks` и `20260727205254_school_lock_deny_direct_access`: hardening ещё не применён. это объясняет расхождение с локальным sql, но само по себе не доказывает публичный доступ к чужим данным;
- установленный hermes — windows, v0.21.3, upstream `98f758ae7e8db83c2bb9214c3b35adf41df15f03`, обычный checkout и venv, не docker;
- на этом точном upstream-коммите проверены `elicitation/create`, маршрутизация в текущую gateway-сессию, возврат `action=accept` с `content={}` и отказ при ошибках/таймаутах. это совместимость по исходникам, не live-проверка кнопок на windows пользователя.

production содержит text, а не jsonb. нельзя менять тип `value`, заново сериализовать всю базу или проводить массовую миграцию данных ради этого этапа.

## 3. рассмотренные подходы

1. **выбран:** ограниченные серверные команды, обязательная mcp elicitation и версионная синхронизация сайта. работает при закрытом сайте; требует защиты всех путей записи затрагиваемых документов.
2. очередь предложений с применением через дашборд. меньше работы с mcp-подтверждением, но пользователь должен открывать сайт; этот вариант не выбран.
3. прямой admin/database mcp или разрешение произвольного `user_data.upsert`. слишком широкие права, нет точного подтверждения и защиты от потери правок; не допускается.

перенос всех задач и целей в новые нормализованные таблицы не требуется. сохраняются существующие ключи и пользовательская модель.

## 4. граница доверия и отдельный доступ

текущий `dashboard-read`, его конфиг и токен остаются только для чтения. новый `dashboard-write` — отдельная edge function и отдельная локальная mcp-запись `dashboard_write`.

утверждённые решения исполнителя:

- отдельный случайный 256-bit write token; его sha256, срок и фиксированный владелец проверяются до доступа к данным;
- тот же фиксированный владелец, что у читателя; owner, произвольный ключ, sql, url и название rpc не принимаются из tool arguments;
- отдельные `DASHBOARD_AGENT_WRITE_TOKEN_SHA256`, `DASHBOARD_AGENT_WRITE_EXPIRES_AT`; владелец берётся из уже настроенного `DASHBOARD_AGENT_USER_ID`;
- срок write token по умолчанию 30 дней; ротация записи не отзывает чтение;
- дополнительное серверное включение записи для владельца; по умолчанию выключено. замена hash, истечение срока или выключение блокируют и новые, и подготовленные записи;
- `verify_jwt=true`, публичный legacy anon jwt и приватный write token в отдельных заголовках; service-role key остаётся только внутри edge;
- https официального проекта, без redirects, query/fragment и browser origin; никаких токенов в url, argv, preview, tool result, git или логах.

edge вызывает только заранее заданные rpc. у mcp-коннектора нет database credentials. новые внутренние таблицы и rpc не доступны роли `anon`; service-only rpc отзываются у `public` и `authenticated`.

подтверждение защищает штатный tool flow от самовольного вызова моделью. это не os sandbox: агент с terminal/file-доступом той же windows-учётки или локальный администратор может прочитать credential-файл и обойти локальный mcp-код. сервер не получает криптографическое доказательство telegram-клика. telegram allowlist, доверенный mcp-клиент и защита локального конфига входят в эксплуатационную границу; документ не обещает защиты от скомпрометированного hermes/ос.

## 5. разрешённые инструменты и поля

пять текущих read tools сохраняются. новые model-facing инструменты:

| инструмент | разрешённый эффект |
| --- | --- |
| `create_task` | одна новая невыполненная задача на конкретную дату |
| `update_task` | разрешённые поля одной невыполненной задачи |
| `move_task` | атомарный перенос одной невыполненной задачи между двумя датами |
| `create_goal` | одна новая цель в конкретном горизонте и периоде |
| `update_goal` | название, приоритет, целевое значение и единица; тип после создания не меняется |
| `move_goal` | горизонт/период и при необходимости приоритет невыполненной цели |
| `set_goal_progress` | числовой прогресс и вытекающий из него статус |
| `complete_goal` | выполнение check- или number-цели без наград |
| `reopen_goal` | возврат check- или number-цели без наград |
| `get_edit_options` | только определения секторов id/name/icon и разрешённые значения полей; без xp/финансов |

`get_edit_options` читает только проекцию `sphere_defs_v1`, при отсутствии — действующий общий список из приложения. неизвестный id сектора не подменяется молча. значение «без сектора» разрешено. изменение определений секторов недоступно.

схемы инструментов закрытые: неизвестные поля отклоняются. нет `confirmed`, `force`, `rawValue`, `owner`, `commit`, `delete` и универсального patch произвольных путей. отдельные модели аргументов для задач и целей.

правила задач:

- `text`: после trim 1–500 unicode code points; `description`: до 10000; `estimatedMin`: целое 1–1440;
- если при создании минуты не заданы — 15, сложность — `medium`, сектор — «без сектора»; все defaults видны в preview;
- `difficulty`: `easy`, `medium`, `hard`; дата строго `yyyy-mm-dd`;
- если дата не задана, фиксируется активный день на этапе prepare: граница 06:00, `asia/yekaterinburg`; при commit дата заново не вычисляется;
- до 100 подзадач, текст каждой 1–500 code points; можно добавлять и переименовывать. существующие отметки выполнения сохраняются; их изменение и удаление подзадач не добавляются;
- `done`, `doneAt`, `actualMin` и поля наград не принимаются; выполненные задачи через hermes не редактируются;
- плановые минуты — длительность, не время начала по часам; школьное расписание не затрагивается;
- любые существующие неизвестные поля сохраняются. перенос сохраняет содержание, id и подзадачи, а не пересоздаёт задачу по одному названию.

правила целей:

- `title`: trim, 1–200 unicode code points, как текущий редактор; `unit`: до 100;
- `priority`: `p1`–`p4`, default `p3`; `type`: `check` или `number`;
- горизонт и период задаются явно: `week` с датой понедельника, `month`, `quarter`, `year`, `5year` с якорем 2026, `life`; неверный/legacy период не заменяется текущим;
- создание: current по умолчанию 0, target по умолчанию 1; у check `done=false`, у number `done = current >= target`, включая отрицательный target. начальный current для number можно задать явно; тип после создания неизменяем;
- числовые `current` и `target` — целые в безопасном для javascript диапазоне, в том числе отрицательные и ноль; знак не теряется. неподдерживаемая legacy величина даёт явную ошибку, не обрезание;
- при изменении current/target числовой цели `done = current >= target`; все побочные изменения статуса входят в preview;
- `complete_goal` для number сохраняет превышенный прогресс, иначе поднимает его до target; для check выставляет `current=1`, `done=true`;
- `reopen_goal` для check выставляет `current=0`, `done=false`; для number требует явного нового current ниже target. молчаливого сброса в ноль нет;
- выполненная цель остаётся в прежнем периоде. перенос и смена приоритета требуют предварительного возврата; переименование разрешено;
- порядок внутри периода/приоритета назначает сервер, в конец группы. пользовательские id, order и schemaVersion не принимаются;
- выполняемые на сайте функции наград не вызываются, монеты/xp/статистика не меняются.

один tool call меняет одну сущность. перенос задачи включает два документа, но остаётся одной операцией. массовое редактирование без отдельных previews не входит в этап.

## 6. идентификация без ошибки «не та задача»

новые задачи/цели получают uuid v4: hermes — на сервере при prepare, сайт — через `crypto.randomUUID()` при локальном создании, в том числе offline. клиентский id принимается после проверки уникальности и не заменяется серверным после синхронизации. существующие корректные id, включая legacy `hg_...`, сохраняются. frontend сохраняет id при редактировании, переносе и перетаскивании, новый id создаёт только для новой сущности/явной копии; при отсутствии криптографического генератора создание не использует `Date.now()` как якобы уникальный id.

для legacy записи без id допустим только snapshot reference вместе с версией исходного документа. сервер проверяет версию **до** разрешения позиции; этот reference не объявляется постоянным id. при первом подтверждённом изменении именно эта запись получает постоянный id. массового изменения всех реальных записей ради выдачи id нет.

read api обратно совместимо дополняется версией источника и доступным id. одинаковые названия, дубли id и неоднозначный target не разрешаются через «первое совпадение». модель перечитывает список и уточняет выбор. поиск по произвольному тексту не является командой записи.

## 7. prepare → подтверждение → commit

1. python создаёт request uuid и сохраняет локальную recovery-запись **до** сетевого запроса; отправляет typed operation в `dashboard-write/prepare`.
2. edge проверяет доступ, серверное включение, схему, лимиты, источник и версии. без изменения задач/целей сохраняет immutable draft и возвращает точный нормализованный preview.
3. draft привязан к владельцу, текущему write credential, request id, операции, исходным версиям, полям, созданным id и хешам будущих документов. срок — 5 минут по серверным часам.
4. python проверяет preview и отправляет клиенту mcp `elicitation/create` form-mode с «было / станет», датой/периодом, defaults и последствиями для статуса. текст берётся из серверного draft, не генерируется моделью.
5. принимается только ответ на конкретный request id от текущего mcp-клиента, `action=accept`. hermes на проверенном коммите возвращает `content={}`: выдуманное поле `approved=true` не требуется. отказ, отмена, timeout, disconnect и неподдерживаемая elicitation ничего не записывают.
6. только после accept python отправляет внутренний commit с draft id и request id, **без** нового patch. этот endpoint не публикуется как tool для модели.
7. edge повторно проверяет доступ; короткая db-транзакция проверяет состояние draft, все версии и хеши, сохраняет документы и receipt атомарно. если меняется сектор, определения секторов входят в read dependencies: изменение `sphere_defs_v1` тоже инвалидирует preview, но не даёт writer права менять этот ключ.
8. tool result содержит подтверждённый результат, id, дату/период и версии. при неизвестном результате не сообщает об успешном сохранении.

ожидание пользователя не удерживает db-транзакцию/row lock. состояние draft: `prepared → committed | cancelled | expired | conflicted`. конфликт/истечение не исправляются скрытым rebase: нужен новый prepare и новое подтверждение.

если источник изменился за время ожидания, commit возвращает `409 conflict`, даже когда кажется, что изменения независимы. это осознанная первая версия, без невидимого merge целого документа.

## 8. mcp и telegram: обязательная реальная остановка

отдельный write server на том же python 3.10+ из существующего venv; новых pip/npm-зависимостей и патча исходников hermes не требуется. reader остаётся отдельным работающим процессом.

- write handshake требует поддерживаемую клиентом form elicitation; при отсутствии capability инструменты записи не выполняются. fallback на текст «ты подтвердил?» или на model argument запрещён;
- reverse json-rpc имеет собственный непредсказуемый id и связывается с одним ожидающим tool call. посторонние/запоздалые ответы не подтверждают ничего;
- во время ожидания обрабатываются ping/cancel; новая mutation возвращает `busy`, не заменяет текущий draft. stdout содержит только protocol frames;
- локальное ожидание ограничено 300 секундами; tool timeout клиента обязан оставлять запас на prepare/commit — 360 секунд. на точном upstream-коммите проверен `mcp_servers.dashboard_write.timeout: 360`, а для самого подтверждения — `elicitation.enabled: true`, `elicitation.timeout: 300`; реальный gateway дополнительно проверяется перед включением записи;
- restart или timeout не возобновляет commit без нового подтверждения. recovery может только узнать статус уже отправленного commit;
- каждое следующее изменение снова вызывает elicitation, независимо от общих режимов/ранее нажатого «always». живой тест должен это подтвердить; если установленный gateway пропускает запрос, релиз записи блокируется;
- gateway должен проверять telegram user id и привязку approval к текущей сессии. групповое/чужое/устаревшее подтверждение не принимается;
- инструкции в названии/описании — обычные данные; управляющие/невидимые символы в preview отображаются безопасно и не превращаются в команды или разметку.

preview ограничен 2500 utf-16 code units **целиком**, чтобы у telegram-обёртки оставался запас. ни поле, ни список изменений не обрезаются. превышение — `preview_too_large`, предложение разделить правку или воспользоваться сайтом; принять неполный preview нельзя. совместимость отображения и отсутствия truncation проверяется отдельно на desktop/mobile telegram.

нативная elicitation не подтверждает произвольный url и не требует нового telegram-бота. изменить конфиг windows и проверить реальный gateway сможет владелец; доступ к нему с mac не предполагается.

## 9. серверные версии и защита от старого сайта

простого `select → json patch → upsert` недостаточно: старый браузер позже отправит весь свой массив. защита обязательна для **обеих** сторон.

выбранная схема сохраняет `user_data.value text`:

- добавить серверную `revision bigint not null` и временное поле `write_base_revision bigint null`; наружу версии передаются десятичными строками, без арифметики javascript;
- для существующих строк начальная revision равна 1; изменение `value` в миграции не требуется;
- trigger назначает следующую revision и серверный updated_at при каждом сохранении. при включённой защите для owner/key требует `write_base_revision=old.revision`; при вставке новой строки — явный `0`;
- после проверки trigger очищает write_base_revision в null: старый upsert, не передающий базовую версию, не может унаследовать допустимый маркер;
- защита применяется только к `goals:yyyy-mm-dd` и `horizons_goals_v2` подключённого владельца; остальные разделы и владельцы сохраняют текущий режим;
- owner/key в update неизменяемы. physical delete защищённого документа запрещён; удаление ключа самим сайтом — версионный tombstone с `value is null`, чтобы старая копия не воскресила данные;
- состояния «нет строки» и «существует tombstone с revision» различаются. уникальный `(user_id,key)` и проверка `0` защищают конкурирующие первые вставки;
- фронтенд использует отдельный bounded cas rpc; owner выводится из `auth.uid()`, а не из параметров. все изменения защищённых ключей одного sync batch сохраняются в одной транзакции;
- service-only commit rpc использует тот же механизм версий, проверяет все исходные/целевые ключи и draft. блокировки берутся в едином порядке `(user_id,key)`; перенос не может закончиться копией без удаления источника или наоборот.

новый ui хранит последнюю реально прочитанную серверную базу и её revision отдельно от dirty local state. нельзя после ошибки просто скачать свежую revision и приложить её к старому локальному документу — это та же потеря данных под видом cas.

при конфликте локальная правка остаётся сохранённой, автоматические retries с новой revision запрещены. пользователь видит «есть изменения с другого устройства/от hermes» и обе версии; может выбрать серверную, либо явно перенести свои правки на текущую версию после просмотра. выбор «оставить мои» не выполняется молча. до разрешения конфликта редактирование этого документа не отправляется в облако; остальные ключи не блокируются.

pull/realtime не затирают dirty state; собственное уведомление не принимается за чужой конфликт. сохраняются offline pending changes, отделение аккаунтов и события `dashboard-sync-applied`. отсутствие base snapshot у старой локальной копии требует явного согласования, а не автоматического first-push поверх облака.

открытая task modal и inline editor привязаны к id/версии, не только к индексу массива. после cloud update нельзя сохранить старый idx поверх другой задачи. все пути создания, переносов, импорта, очистки, перетаскивания и backup restore проверяются; общий reset не получает обход guard. существующие браузерные операции и награды сохраняются по смыслу, атомарность начисления наград не объявляется решённой этим этапом.

старый js после включения защиты получает явный отказ записи, а не ложный success. новый js показывает необходимость обновить страницу; на старой вкладке возможен старый общий индикатор ошибки — это безопасный отказ, а не гарантия красивого уведомления в коде, которого там ещё нет.

## 10. хранение служебного состояния и права

добавляются внутренние таблицы для per-owner включения защиты/записи, drafts/receipts и ограничений частоты. они размещаются в неэкспонируемой схеме; rls включена как дополнительная защита. публичных policies «читать всем» нет.

- browser cas rpc: `security invoker`, доступ только `authenticated`, owner через `auth.uid()`, существующие owner policies сохраняются;
- prepare/commit/status/cancel: только `service_role`, `security invoker`, никакого `public execute` по умолчанию;
- узкий trigger/helper, которому нужно прочитать внутренний флаг, может иметь `security definer` только с пустым search_path, явными schema names и отозванным внешним execute; он не меняет owner и не является универсальной функцией записи;
- перечень разрешённых ключей и ownership проверяются в db, не только в typescript. метаданные `user_metadata` не участвуют в авторизации;
- draft хранит нормализованную команду, preview, версии и хеши ожидаемых документов, не копии всей базы; commit восстанавливает будущие значения на сервере и rpc проверяет их хеши;
- audit содержит actor `hermes`, operation, target id, request id, изменённые поля, версии и outcome. не содержит токенов, полных документов, provider body и содержимого других разделов;
- payload истёкших/завершённых drafts очищается не позднее суток, подробные receipts/audit — через 30 дней. минимальный реестр использованных request ids сохраняется до удаления аккаунта: owner, request id, hash команды/credential generation, terminal outcome, target id, версии и время, без текстов задач/целей. cleanup не удаляет этот реестр. реализация должна предоставить исполнимый серверный cleanup и проверить его; конкретный механизм выбирает builder без внешнего платного сервиса. если нужен новый extension/job, его установка входит только в отдельно разрешённый deployment.

новые миграции создаются штатным `supabase migration new`; перед применением сравниваются локальная/удалённая history и фактический sql. исходные migration names не переименовываются. production sql на этапе дизайна не выполняется.

## 11. повторы, лимиты и ошибки

request id сохраняется локально в отдельном sqlite outbox вне git, с теми же windows acl, что и credentials; sqlite входит в python stdlib. секрет в outbox не дублируется.

- одинаковый request id с тем же содержимым возвращает прежний draft/receipt; с иным содержимым — `409 request_mismatch`;
- повторный commit одного draft возвращает прежний receipt без второго изменения;
- после удаления подробного receipt старый request id не становится новым: prepare/commit дают `410 request_retired`, status возвращает только сохранённый terminal outcome/id/версии и признак `receipt_expired`. неизвестный outbox не преобразуется в новое действие. повторный request id с другой командой/credential generation отклоняется независимо от возраста;
- при сетевом timeout после commit коннектор сначала запрашивает status по прежнему request id. новый request id и новая запись не создаются автоматически;
- неизвестный результат хранится после restart и явно сообщается. до его разрешения соответствующая mutation не повторяется;
- новое создание с полностью совпадающей сущностью в том же дне/периоде требует отдельного явно помеченного preview дубликата; нормальный повтор запроса не используется для обхода idempotency;
- одна pending mutation на локальный write server; серверный предел 20 активных drafts на owner, 120 новых prepares и 60 commits за 10 минут; одинаковые повторы request id не расходуют квоту повторно;
- request до 32 kib, защищённый документ до 4 mib, browser cas batch до 64 документов и 4 mib суммарно; превышение — validation error без обрезания;
- неизвестная/повреждённая структура, неоднозначный target и невалидное существующее поле не превращаются в пустой список; изменяемая сущность проверяется без нормализации чужих сущностей;
- expected errors: `401 unauthorized_or_expired`, `403 write_disabled/origin_not_allowed`, `409 conflict/request_mismatch/busy`, `410 draft_expired`, `413 request_too_large`, `422 invalid_change/preview_too_large`, `429 rate_limited`, `502 upstream_unavailable`;
- ошибки не раскрывают token, sql, server key, сырой response или чужие данные. фраза «сохранено» появляется только после commit receipt.

## 12. совместимость, поставка и откат

порядок поставки — часть безопасности, а не произвольная перестановка шагов:

1. после утверждения дизайна — tdd implementation plan и отдельный github issue для подтверждённого lost-update риска; русское описание в нижнем регистре, без credentials.
2. отдельные логические изменения поверх reader. пока pr #70 открыт, следующая ветка/pr имеет его ветку в base; после его merge — retarget/rebase на main, чистый diff и повторные тесты. читатель не мержится автоматически.
3. локальные/изолированные db tests, обратная совместимость read api, frontend/backend/stdlib mcp и typecheck/lint. только затем pr на проверку.
4. сначала сверить production migration history с фактическими policies/triggers и локальным sql: обнаруженный drift нельзя скрыть `migration repair`, переименованием или слепым replay. согласовать отдельное корректирующее изменение после diff/тестов. только после этого — отдельно разрешённая additive migration revision и служебных объектов, guard/write выключены; существующий сайт продолжает работать.
5. отдельно разрешённый deploy нового frontend с cas/конфликтами и чтением revisions; проверить фактически опубликованные assets и рабочий вход. старый сайт не отключается вслепую.
6. отдельно разрешённый deploy `dashboard-write`, всё ещё disabled. существующая `dashboard-read` не заменяется; её additive обновление для revisions поставляется только проверенным отдельным изменением.
7. владелец запускает новый `--configure-write` в **новом** credential-каталоге на windows; читатель не перезаписывается. yaml объединяется с config, не заменяет его. wireup включает elicitation и достаточный tool timeout, только перечисленные инструменты; sampling/resources/prompts для writer не нужны.
8. проверить совместимый frontend, сохранность pending локальных данных и telegram allowlist. при неизвестной base revision сначала разрешить конфликт. после явного разрешения включить per-owner guard, затем запись; оба должны быть активны одновременно для любых commits.
9. live acceptance с временными сущностями допускается только после отдельного разрешения владельца; до него — mocks и изолированная db. реальные текущие задачи/цели не используются как расходные.

откат: первым действием выключить write, отозвать write token и закрыть drafts. reader остаётся рабочим. cas guard сохраняется до явного решения, чтобы старые вкладки не затёрли уже принятые правки. откат к legacy frontend требует отдельной контролируемой процедуры с резервной копией; удаление version columns/receipts не является штатным первым шагом.

## 13. критерии приёмки и будущие проверки

- создание/редактирование/перенос задач и все выбранные операции целей видны на сайте после подтверждения; закрытый сайт не мешает записи;
- до accept, после decline/cancel/timeout/disconnect и из чужой сессии изменённых пользовательских строк нет;
- новый patch/target после preview, `confirmed=true`, подставленный draft, старый ответ и повторный click не меняют согласованное действие;
- нет silent approval в режиме off/always и при отключённой/отсутствующей elicitation; неподтверждённая совместимость блокирует выпуск writer;
- конфликт браузер ↔ hermes, hermes ↔ hermes, две вкладки, offline reconnect, новая строка ↔ новая строка, tombstone ↔ stale insert: нет потери правок/дубликатов; конфликт требует нового осознанного действия;
- move task all-or-nothing; отказ на одном ключе откатывает второй; consistent lock order и bounded transactions;
- устаревший preview после смены сектора/исходного документа не применяется, повторно показываются актуальные значения;
- отрицательные/нулевые числовые цели, выполненные/возвращённые цели и границы пн–вс/06:00/месяца/пятилетки сохраняют описанную семантику;
- чтение и нерелевантные ключи не сломаны; доступ другого owner, anon, generic sql/key, school/tracker/coins/xp/write scope не расширился;
- postgres integration tests проверяют реальные rls/grants/triggers/cas/rollback/idempotency, не только mock fetch; security advisor проверен по новым объектам и нерелевантные старые warnings выделены отдельно;
- frontend tests, оба backend suites с собственными deno.json, python tests, typecheck/lint, production-equivalent config/import check и secret scan зелёные;
- отдельные живые проверки telegram desktop/mobile: полный читаемый preview, каждый раз новые кнопки, refusal/timeout/restart и отсутствие скрытой обрезки. локальные tests не объявляются доказательством этих проверок;
- live тестовые задача и цель, если будут разрешены, явно помечаются и удаляются административным контролируемым способом; после очистки сверяются исходные количества/id реальных сущностей. delete tool для модели ради очистки не добавляется;
- отчёт разделяет код, ci, опубликованные assets, включённые права и реально проверенный windows/telegram. автоматического merge нет.

## 14. дополнительно утверждённые решения исполнителя

помимо явно выбранных пользователем `1а, 2а, 3а`: отдельный write token на 30 дней; draft на 5 минут; одно подтверждение на одну сущность; защищённые завершённые задачи; запрет удаления/изменения отметок подзадач; явный current при возврате числовой цели; отказ при слишком длинном preview вместо truncation; per-owner cas guard со старой вкладкой в fail-closed режиме; временные live сущности только с отдельного разрешения.

точные имена внутренних rpc/таблиц, разбиение модулей и механизм cleanup оставлены builder при сохранении описанных гарантий. выбор новых внешних сервисов, расширение прав на другие разделы или ослабление подтверждений не делегируются.

независимый builder check выполнен; после уточнения сохранения использованных request ids и offline uuid повторная проверка не оставила существенных вопросов. self-review отделил локальную миграцию от её фактического отсутствия в production и проверил имя настройки mcp timeout на точном upstream-коммите.

до изменений кода повторно проверена база: frontend 537/537, school backend 108/108, read backend 14/14, python-коннектор 10/10; check/lint обеих edge functions прошли. первый общий вызов `deno test` из корня не использовал отдельный import map школы; корректные запуски `deno task test` из каталогов каждой функции прошли без изменения кода. это проверка существующей основы, не доказательство готовности ещё не реализованного writer.
