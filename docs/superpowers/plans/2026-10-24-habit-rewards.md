# награды полезных привычек 2/1 — план реализации

> для исполнителя: обязательный навык — `superpowers:executing-plans` для самостоятельного исполнения либо `superpowers:subagent-driven-development`, если пользователь выберет делегирование. выполнять задачи через red → green, без массового начисления за прошлое.

**цель:** полная полезная привычка даёт 2 монетки, половина — 1; изменения отметок корректируют реально выплаченную награду без накрутки.

**архитектура:** чистая модель наград вычисляет дельту из ledger в `coins_v1`, отдельный адаптер координирует локальную пару отметка/баланс с восстанавливаемым журналом. ui трекера посылает явное целевое состояние; история профиля понимает подписанную корректировку. обычные штрафы и остальные денежные операции не переписываются.

**стек:** vanilla javascript/umd, существующий gamification storage, web locks / атомарный indexeddb fallback, `node:test`; без backend-миграций.

**спецификация:** [утверждённый дизайн, раздел «награды трекера»](../specs/2026-10-24-eye-breaks-design.md). [разминка](2026-10-24-eye-breaks.md) — отдельная подсистема, не зависимость наград.

## общие ограничения

- полный mark `1` → reward `2`; половина `0.5` → `1`; пустой `0` → `0`.
- цикл ui остаётся `0 → 1 → 0.5 → 0`; повтор вызова одной команды идемпотентен.
- только полезные привычки; штрафы вредных привычек, покупки и награды других модулей не меняются.
- legacy без ledger считается неоплаченным: загрузка не выдаёт монет, обратный переход не списывает невыданные.
- дельта меняет `balance` и чистый `earned`; `spent` не растёт от корректировки; баланс может стать отрицательным при возврате уже выплаченного.
- нет обещания распределённой транзакционности разных устройств: существующий sync по ключам её не даёт.
- служебный журнал и leases не уходят в облако/backup. auth, rls и школьный адаптер не меняются.
- обе версии gamification совместимы; не объединять их попутно. github/коммиты по-русски и с маленькой буквы, без соавторства; merge только по отдельному решению.

## фокус проверки

1. legacy mark зелёный, но никогда не оплачен: переход в половину начисляет 1, а не списывает 1 — задача 1.
2. отметка многократно меняется или повторяется команда: нет повторной выплаты и раздувания `earned` — задачи 1–2.
3. процесс упал между двумя записями либо упал storage: журнал восстанавливает одну принятую операцию и не теряет посторонние монеты — задача 2.
4. две вкладки/двойной click/смена аккаунта: нет параллельных habit-writes и применения журнала другого владельца — задачи 2–3.
5. имя привычки/backup/история повреждены или содержат html: нет xss, NaN-баланса и некорректного знака операции — задачи 1 и 3.

## файлы и границы

- `habit-rewards-core.js`: чистые валидация команды, расчёт дельты и применение к свежему балансу.
- `habit-rewards-lock.js`: самостоятельный локальный mutex с web locks / атомарным indexeddb fallback, не импортирует eye-модули.
- `habit-rewards-store.js`: журнал и безопасное восстановление пары `coins_v1` / `tracker_v1`.
- `tracker.html`: async вызов сервиса только в good-ветке, pending и понятная ошибка.
- `profile.html`: безопасное отображение нового типа истории монет.
- `supabase-sync.js`: исключение `_habit_reward_` служебных данных, без общей переделки sync.
- `test/habit-rewards-*.test.cjs` и существующие security/sync/ui tests.

### задача 1: чистая модель награды и ledger

**файлы:** создать `habit-rewards-core.js`, `test/habit-rewards-core.test.cjs`.

**интерфейсы:**

- `validateCommand({operationId, habitId, date, expectedMark, targetMark, owner, at}) -> Command`; валидная календарная дата, разрешённые marks, непустой id привычки, uuid операции и валидный iso timestamp.
- `rewardForMark(mark) -> 0|1|2`.
- `prepareChange(tracker, coins, command) -> {command, delta, previousReward, targetReward, noOp}`; привычка должна существовать в `tracker.good`; stale expectedMark не превращается в ещё один toggle.
- `applyCoinChange(freshCoins, change) -> Coins`; новый ledger `coins.habitRewardsV1[markKey] = {paid, operationId, targetMark, at}`. та же операция повторно не меняет монеты, запись `paid:0` остаётся для идемпотентности.
- `applyTrackerChange(freshTracker, change) -> Tracker`; изменяет только одну отметку, сохраняет имена, привычки и все чужие даты.

- [x] red-тесты цепочки `0→1→0.5→0→1`: дельты `+2,-1,-1,+2`, итоговый `earned` ровно 2, `spent` прежний, ledger соответствует последнему состоянию.
- [x] red-тесты legacy: исходная зелёная без ledger → половина даёт `+1`; исходная половина без ledger → пусто даёт `0`; простое чтение/prepare не пишет и не начисляет.
- [x] red-тесты duplicate operation, stale mark, неизвестной/вредной привычки, некорректной даты, нечисловых балансов и поддельного ledger; входные объекты не мутируют.
- [x] запустить `node --test test/habit-rewards-core.test.cjs`, получить red; реализовать чистые операции.
- [x] история новых операций: `{type:'adjust', amount: signedDelta, reason, date: at, operationId}`; нулевая дельта не создаёт лишнюю строку. сохранённые reward ledger и unrelated coin fields не теряются.
- [x] focused green; коммит `рассчитывать награды привычек по реально выплаченным монетам`.

### задача 2: локальная операция с восстановлением

**файлы:** создать `habit-rewards-lock.js`, `habit-rewards-store.js`, `test/habit-rewards-store.test.cjs`.

**интерфейсы:**

- `HabitRewardsLock.create({locks,indexedDB,now,uuid}).withLock(owner, work) -> Promise<Result>`; взаимное исключение habit-операций одного владельца в браузере; no-storage/no-lock ошибка, не псевдоатомарный localStorage read/write.
- `HabitRewardsStore.create({get,set,runtimeStorage,getOwner,withLock,now,uuid}) -> {setGoodMark, recover}`.
- `setGoodMark(habitId,date,targetMark,{expectedMark,operationId}) -> Promise<{tracker,coins,delta}>`.
- локальный `_habit_reward_tx_v1` содержит owner, принятую command и рассчитанные reward-данные; не полный снимок всех монет для будущей перезаписи.
- `recover()` выполняется под тем же lock, до принятия следующего изменения; не трогает journal другого owner.

- [x] red-тесты двух параллельных good-запросов, повторного operationId, корректного token release и недоступного атомарного fallback; journal всегда связан с владельцем.
- [x] inject failure в каждую запись: journal, coins, tracker, удаление journal. после reload recovery не дублирует дельту и не начинает исторический backfill; отказ recovery блокирует новую операцию с понятной ошибкой.
- [x] проверить, что другие монеты/поля, добавленные между первым шагом и recovery, сохраняются. повторное чтение свежих coins и ledger обязательно; восстанавливать весь старый coin snapshot запрещено.
- [x] реализовать порядок: lock → восстановление предыдущего журнала → свежие tracker/coins → проверка expectedMark → journal → идемпотентная coin-дельта → целевая tracker-отметка → проверка пары → удаление journal → release в finally.
- [x] `Gamification.storeSet` может синхронно вызвать обработчики достижений: не сохранять повторно устаревшие coins после этих событий. legacy/current gamification используют один договор storage; проверять обе версии harness.
- [x] выполнить focused тесты задач 1–2; коммит `защитить начисление привычек журналом и блокировкой вкладок`.

### задача 3: трекер, история и граница синхронизации

**файлы:** изменить `tracker.html`, `profile.html`, `supabase-sync.js`; создать `test/habit-rewards-ui.test.cjs`; расширить `test/supabase-sync.test.cjs`, `test/security-rendering.test.cjs`.

**интерфейсы:** текущий `toggleMark(habitId,dateStr,type)` остаётся ui-входом. good-ветка превращает один click в явную command с одним operationId и expectedMark; bad-ветка сохраняет прежнюю семантику. модуль профиля отображает `adjust` по знаку `amount`, `earn/spend` по старому контракту.

- [x] red vm/dom-тесты: click зелёной даёт +2, следующий оранжевой -1, снятие -1; pending отключает повтор для этой отметки; повтор callback с прежним id не ещё один toggle; ошибка не выдаётся за сохранённую отметку.
- [x] red-тесты обычной загрузки и `dashboard-sync-applied`: только render/recover принятого журнала, без выплаты за прошлые marks. смена user не запускает старый journal.
- [x] red-тесты имени `<img …>` и подписанной корректировки `-1/+2`: html экранируется, знак и css-класс правильны и в первых 15 строках, и в «показать все»; устаревшие `earn/spend` не ломаются.
- [x] red-тесты sync/backup: `_habit_reward_` исключён; ledger в `coins_v1` синхронизируется как часть пользовательского состояния. active journal не экспортируется, удаление привычки не делает массовый неявный refund.
- [x] подключить новые модули до inline-контроллера трекера, показать короткую легенду наград `2 / 1`, pending и доступную ошибку. не менять marks вредных привычек и не смешивать награду с дневным score.
- [x] добавить узкое исключение служебного префикса в sync и безопасный форматтер истории в обе точки render профиля, без несвязанного рефакторинга.
- [x] focused green и `node --test test/*.test.cjs`; коммит `начислять монеты за полезные привычки и показывать корректировки`.

## самопроверка плана

- правила 2/1, legacy, идемпотентность и чистые totals → задача 1.
- journal, восстановление, повторное чтение, несколько вкладок, owner → 2.
- ui, история, безопасность вывода и служебные исключения → 3.
- все пять классов ошибок покрыты red-тестами; обе версии gamification проверены без объединения; полная приёмка → 4.
- интерфейсы используют одни и те же поля `operationId`, `expectedMark`, `targetMark`, `paid`; план не добавляет автоматические монеты за таймер разминки.
